# Build Spec: "Talk to Your Building" Agent (Synera Track 01)

Audience: an orchestrating AI that builds this repo in phases, with sub-agents or sequential work.
Base: the official kit (`starter_agent/`, `benchmark/`, `data/`). Extend it, do not rewrite it.
Language: Python 3.12, `uv`, Anthropic API. Model and effort are configurable (default: see `starter_agent/agent.py`).

## 0. Hard rules (from the challenge README)

- Answers must be generated by the agent running on the data. No hand-labelling, no hard-coding to test buildings.
- Works on ANY building in the `building.json` format (Sunday building is unseen).
- One documented command runs everything without manual steps (`BENCHMARK.md`).
- Final scored line of every reply: `Answer: <value>` (last line starting with `Answer:` counts). Exactly one number for numeric answers, no ranges.
- Submission = one CSV (`question_id,answer`), UTF-8, header row, max 5 MB. The brief PDF mentions `answers.json`; the README says CSV. Support BOTH writers and confirm with organizers.
- Never commit `.env` or API keys. OSM-derived output stays under ODbL with attribution.
- Scoring weights: works 55, interaction 25, creativity 10, demo 10.

## 1. Architecture

```
user (text / voice) -> UI -> agent loop (Claude + tool runner) -> tools.py -> building_map.py (deterministic core) -> building.json (+ edits)
                                   |                                    |
                               prompts/skills                     geometry.py (shapely)
                                                                  viewer / 3D
benchmark path: question -> kind classifier -> kind skill (prompt) -> tools -> formatted "Answer:" line
```

Principle: Claude never invents facts. Every number, room id and route comes from a tool.
No external database is required: `building.json` is loaded into an in-memory model (`BuildingMap`). Optional: SQLite/JSON file for edit history and moved assets.

## 2. Data model facts the core must implement exactly

- Units metres, x right, y up, one XY frame per building (floors stack; some Swiss Dwellings floors are centred per floor).
- `level` integer (0 ground, -1 basement). `elevation_m` per floor.
- Space types: room, corridor, stair, lift, hall, outdoor. Openings: door | opening | entrance (`space_ids` contains `"outside"`).
- Opening has `width_m`, `step_free`, `position`. Vertical connectors: stairs | lifts with `floor_ids`, `space_ids`, `step_free`.
- Assets: category furniture | fixture | machine | equipment, with `space_id`, `position`, footprint.
- Route graph (kit 1.1.0, README section 3, must match dataset to the centimetre):
  - nodes: one per space at `representative_point()` of its polygon (`buffer(0)` if invalid), plus one per opening
  - walking inside a space: an opening lands 30 cm inside the space (nearest point of `buffer(-0.30)`); the step to the landing counts
  - between the space's centre point and its openings: shortest walk on `buffer(-0.15)` via a visibility graph of the points and the shrunken corners (segment clear if `buffer(0.02)` covers it); a corridor you pass through is walked door to door; edge lengths rounded to 3 decimals
  - stairs 2 m per metre climbed, consecutive stops only; lifts 15 m once per ride + 1 m per metre climbed, every pair of stops; height = difference of `elevation_m`
  - step-free drops every stair and every opening with `step_free: false`; closed items can't be used
  - keep parallel connections (stair and lift between same spaces, two doors between same rooms)
  - no way round the outside: entrances join nothing; parts that only meet outside are `reachable: false`
- Space names usually contain the room ref (`Office 0.30`). Asset names unique per building.

## 3. Tools to implement (name, purpose, key params, returns)

All tools return compact JSON (token cost matters). All accept ids OR human refs/names and resolve them; ambiguous input returns candidates instead of guessing.

### 3.1 Lookup (Level 1)
| Tool | Purpose |
|---|---|
| `building_overview` | floors, connectors, entrances, closures, counts (exists) |
| `search_building(query, floor?, room_type?, category?, type?)` | fuzzy search rooms/assets by name, ref, type; synonyms ("loo" -> toilet, "printer" -> print_room/3D printer) (exists, improve) |
| `get_space(id_or_ref)` | type, room_type, floor, area_m2, centroid, bbox, openings (with widths), neighbours, assets inside |
| `list_spaces(floor?, room_type?, min_area?)` | filtered list |
| `get_asset(id_or_name)` / `list_assets(type?, space?, floor?)` | asset details |
| `count_assets(type, floor?)` | counts (warm-up `count` kind) |

### 3.2 Geometry (benchmark "plan facts" + "spatial reasoning")
| Tool | Purpose / definition |
|---|---|
| `room_area(space)` | polygon area in m2 |
| `largest_room(room_type, floor)` | argmax area, returns name + m2 and the runner-up |
| `floor_area_total(room_type, floor)` | sum of areas of all rooms of that type on the floor |
| `door_widths(space)` | widths of all openings of a space |
| `room_centroid_3d(space)` | centroid of polygon at floor `elevation_m` |
| `straight_line_3d(a, b)` | Euclidean distance between the two centroids (3D, includes elevation) |
| `room_above(space)` / `room_below(space)` | space on the next floor up/down whose outline covers most of this room's outline (max overlap area). Only valid when floors share one XY frame; otherwise say so |
| `shared_walls(space, min_len=1.0, tol=0.35)` | other spaces on the same floor where >= 1 m of one outline lies within 0.35 m of the other. Corridors, stairwells, lifts are excluded from the count (report them separately). Door or no door is irrelevant |
| `adjacent_spaces(space)` | neighbours via door (graph) vs. via wall (geometry), clearly separated |

### 3.3 Routing (Levels 2 and 3)
| Tool | Purpose |
|---|---|
| `find_route(from, to, step_free?, min_door_width?, no_stairs?, avoid?, via?[])` | shortest path, node id list, `space_path`, `element_path`, length_m, human directions. Returns `reachable:false` with a reason when impossible (exists, extend with min_door_width, avoid, multi-building) |
| `tour(start, stops[], ordered=true)` | multi-leg route, per-leg and total length |
| `nearest(from, asset_type|room_type, constraints)` | nearest target by ROUTE distance (not straight line), returns top-3 with margins |
| `errand(start, pickups[], dropoff, constraints)` | chains nearest-with-asset, then dropoff (e.g. "stove from the closest room that has one, carry to largest meeting room on floor 1, stairs allowed") |
| `reachable_spaces(origin|entrance, step_free?, min_door_width?, no_stairs?, closed?[], floor?, room_type?)` | set + count of reachable rooms. Trolley rule: no stairs/steps (lifts allowed), every door passed must be >= width. Wheelchair rule: step-free only |
| `exit_distance(space, closed?[])` | route-model distance to nearest entrance |
| `what_if_door(space_a, space_b, floor_filter, metric)` | ephemeral copy of the building, door at the midpoint of the shared wall segment, recompute exit distances, count rooms on the asked floor whose walk-out is shorter by more than 1 m. Never mutates the real building |
| `compare_routes(before, after)` | diff of two route results (for "what changes?") |

### 3.4 Edit / React (Levels 2, 4, 5)
| Tool | Purpose |
|---|---|
| `set_closed(element, closed)` | lift, stair, door, room closure (exists) |
| `list_closures()` / `reopen_all()` | state management |
| `impact_of_closure(element, sample_pairs?)` | "what changes": newly unreachable rooms, longest detours, affected step-free routes |
| `add_door(space_a, space_b, position?|midpoint, width=0.9, step_free=true)` | validates shared wall, writes edit (exists, harden) |
| `remove_door(id)` / `add_space` / `remove_space` / `resize_space` | structural edits with validation |
| `move_asset(asset, to_space|position)` / `add_asset` / `remove_asset` | live inventory ("this is now here") |
| `preview_edit(...)` -> `apply_edit(id)` -> `undo()` | two-step confirmation: show what will change, then commit. Edit log with who/when |
| `validate_building()` | schema check, polygons valid, openings reference real spaces, every space reachable from an entrance (report islands), stair/lift stops on consecutive floors |
| `save_building(path)` | writes `building_edited.json` (never overwrite the input) |

### 3.5 Build from floor plans (Level 4)
| Tool | Purpose |
|---|---|
| `ingest_floorplan(image|pdf|svg, floor_level, scale?)` | send the image to a vision model, get a draft `spaces/openings/connectors` in the dataset JSON format |
| `calibrate_scale(pixel_dist, real_dist)` | metres from pixels |
| `detect_rooms` / `detect_doors` (vision + heuristics, optional cv2 contour step) | structured extraction with confidence per element |
| `assemble_building(floors[], connectors[])` | stack floors, align XY frame, link stairs/lifts |
| `repair_building()` | fix common issues found by `validate_building` (unconnected rooms, open polygons, missing entrance) |
| `review_building()` | render overlay of extracted geometry on the source image so the user can confirm or correct by chat |
Target: new building usable in minutes. Always run `validate_building` before accepting.

### 3.6 Multi-building (Level 3)
| Tool | Purpose |
|---|---|
| `load_buildings(dirs[])` / `list_buildings()` | several `BuildingMap`s in one session |
| `link_buildings(a_space, b_space, kind=walkway|outdoor, length_m, step_free)` | walkway edges between buildings |
| All routing/search tools take an optional `building` argument and may cross buildings via links |

### 3.7 Views and output
| Tool | Purpose |
|---|---|
| `show_route(route)` | PNG per floor with route drawn (exists) |
| `render_floor(floor, highlight[])` | plan with highlighted rooms/assets |
| `export_3d_scene()` | JSON for a three.js viewer: extruded floors by `elevation_m`/`height_m`, animated route polyline, assets as markers |
| `describe_route_for_humans(route, style=landmarks|room_numbers)` | "turn left at the printers", with room numbers as fallback, step-free hints, floor changes |

### 3.8 Level 5 add-ins (pick one, do it well)
Pick 1: moving assets (`move_asset` + scan/barcode endpoint), forklift mode (wide doors, blocked aisles as closed zones), accessibility profiles (width, quiet routes), multi-user edits (versioned edit log + SSE), AR (QR at doors for localisation), phone capture. Voice in/out counts for Interaction regardless of the add-in.

## 4. Harness (agent loop, API, runtime)

- `answer(building_directory: Path, question_text: str) -> str` is the single entry point used by `benchmark.evaluate`. Returns the full reply that ends with `Answer: ...`.
- Anthropic SDK tool runner. Fresh conversation per benchmark question; persistent conversation with copied history in chat mode.
- Prompt caching on the system prompt + building overview. Keep tool outputs compact. Cap tool-call count and tokens per question; log usage.
- Two modes:
  1. `benchmark` mode: no clarifying questions, deterministic, low effort where possible, strict answer formatting.
  2. `chat` mode: may ask back, shows its understanding before edits, streams to UI.
- Optional hybrid fast path: a cheap classifier maps the question to one of the 9 benchmark kinds, then runs a kind-specific solver (tools called directly) and lets the LLM only phrase the reply. Fall back to the full agent when unsure. Compare both on dev.
- Self-check step before answering: recompute numbers, check unit, check "exactly one number", check the chosen room beats the runner-up.
- Model choice by kind (cheap model for lookups, bigger for errands/what-if). Evaluate cost vs. score on dev.
- Retries on API errors, per-question timeout, resume support (skip already answered ids).
- Environment: `.env` (`ANTHROPIC_API_KEY`), `UV_LINK_MODE=copy` on OneDrive paths (project lives in `C:\dev`).

## 5. Prompts and skills (markdown files loaded into the system prompt or by kind)

- `prompts/system.md`: role, "never invent facts, always call tools", ask only what is needed, show understanding before edits, prefer room numbers plus a landmark, mention step-free by default for accessibility questions.
- `prompts/answer_format.md`: the `Answer:` rules per kind (see section 6).
- `skills/<kind>.md` per benchmark kind: definition, which tools to call, edge cases, example from train data, common mistakes. Kinds: `largest_room`, `floor_area_total`, `errand`, `wide_delivery_count`, `step_free_reachable_count`, `room_stacked`, `shared_walls_count`, `straight_line_3d`, `what_if_door`, plus warm-up kinds `locate`, `count`, `route`, `route_step_free`, `route_with_closure`, `tour`.
- `prompts/clarify.md`: vague request policy (see section 7).
- `prompts/build_from_plan.md`: instructions for the vision extraction step with the JSON schema.

## 6. Answer formats and scoring tolerances

| Kind | Answer line | Tolerance |
|---|---|---|
| `largest_room` | room number or full name FIRST, then area in m2 | area +-5%, expected room named before any runner-up |
| `floor_area_total` | one number (m2) | +-5% |
| `errand` | one number (metres) | +-1% (min 1 m) |
| `wide_delivery_count`, `step_free_reachable_count`, `shared_walls_count`, `what_if_door` | one integer | exact |
| `room_stacked` | expected room, before any runner-up | name match |
| `straight_line_3d` | one number (metres) | +-2% |
Warm-up kinds: route within 1% of `optimal_length_m`, locate finds the right asset, count has the right number.
No `Answer:` line, a range, or several numbers in the line = wrong.

## 7. Interaction design (25 points)

- Asks only what it needs. Ambiguous target ("the printer" with 3 matches): list candidates with floor and room, ask once. Wrong input ("room 9.99"): say it does not exist, offer nearest matches.
- Shows what it understood before changing anything ("I will add a door between 2.03 and 2.04 on floor 2 at the shared wall, 0.9 m wide. Confirm?").
- Directions a person can follow: landmarks plus room numbers, floor changes ("take the lift"), step-free noted, total metres and rough minutes.
- Handles changes of mind and corrections without restarting.
- Voice in/out (ElevenLabs) as optional layer over the same agent.

## 8. Evaluation harness

- `uv run python -m starter_agent.evaluate data/dev --oracle` must stay at ~100% on warm-up (route lengths match to the centimetre).
- Unit tests per tool against `inputs`/`answer` in `data/{train,dev}/*/questions.jsonl` (free, no API). Target 100% on train+dev for tool-level oracle per kind before using the LLM.
- `uv run --env-file .env python -m benchmark.evaluate data/dev --per-kind 3` for the live agent; track score per kind and cost per question.
- `benchmark.score` is the official scorer; run it on dev to check formatting.
- Final: `uv run --env-file .env python -m benchmark.evaluate data/test --agent <module>:answer --submission-csv team_<n>.csv`.
- Write `BENCHMARK.md` with the exact single command for the Sunday building and the output format.

## 10. Build phases (for the orchestrator)

1. Environment and baseline: `uv sync`, oracle eval = ~100% warm-up, dev baseline recorded.
2. `geometry.py` + tools for `largest_room`, `floor_area_total`, `straight_line_3d`; tests against dev.
3. `reachable_spaces`, `wide_delivery_count`, `step_free_reachable_count`, `exit_distance`; tests.
4. `room_above/below`, `shared_walls`; tests.
5. `nearest`, `errand`; tests.
6. `what_if_door` (ephemeral copy); tests.
7. Prompts/skills per kind, answer formatter, live eval per kind, cost tuning, hybrid fast path.
8. `BENCHMARK.md`, CSV writer (+ optional JSON), full dev run, freeze.
9. Chat UI with 2D view, route drawing, edit preview/confirm; then 3D and voice.
10. Level 4 build-from-plan pipeline with validation; Level 3 multi-building links.
11. One Level 5 add-in. Demo video script and tech write-up.

Acceptance for each phase: tests green on train+dev, no hard-coded ids, tool outputs compact, changes committed.
